# internity Performance Report

The established comparison tables later in this report were generated by
[`scripts/perf_report.rs`](../scripts/perf_report.rs). Re-run it to refresh
those tables; the instruction-count comparisons and provisional observations
are separate.

## Instruction-count comparisons for threaded interning and freeze

These matched local `benches/internity.rs` Callgrind runs measured the `Ir`
metric for a **single operation**, excluding benchmark setup. They used the
same x86-64-v3 release profile, rustc 1.98.0-nightly, and AMD EPYC 7763 host.
Run `cargo bench -p internity --bench internity -- --gungraun` to reproduce the
current cases. The rows compare implementations, not concurrent throughput:
Callgrind cannot measure contention, writer stalls, or wall-clock latency.

For P1, the same string and byte cases were measured with shared-read hits and
write-lock rechecks, then with upgradable-read hits and atomic upgrades:

| One threaded operation | Shared read + recheck | Upgradable read + upgrade |
|---|---:|---:|
| String hit | 256 | **251** |
| String miss | 626 | **606** |
| Byte hit | 256 | **255** |
| Byte miss | 766 | **744** |

The upgradable protocol was restored: it reduces instructions in all four
cases, at the cost of serializing same-shard interners even on hits. Ordinary
`get` readers can still share access. No concurrency or latency improvement is
claimed from this single-threaded instruction-count evidence.

For P2, both sides use that upgradable protocol and the same 1,001-string
setup. A shared freeze copies all 64 shards when no live unchanged snapshot
is available; an unchanged shared freeze retains the previous reader in the
benchmark setup:

| One operation | Copy every shared freeze | Reuse unchanged snapshot |
|---|---:|---:|
| First shared freeze | **30,211** | 30,704 |
| Repeated unchanged shared freeze | 35,983 | **163** |
| Frozen threaded lookup | **110** | 111 |
| String miss / hit | **606 / 251** | 610 / 252 |
| Byte miss / hit | 744 / **255** | **713** / 262 |

The cache gives a large instruction-count reduction specifically when a
shared snapshot is still live and no distinct string has been inserted since
it was captured. First shared freeze, frozen lookup, and several interning
cases cost slightly more instructions. A weak cache does not retain the
snapshot once all readers drop. These measurements do not establish an
improvement for workloads dominated by new snapshots or writes.

`internity_compare/freeze-concurrent` complements these single-threaded counts
with 2-, 4-, and 8-thread wall-clock cases in which every caller reaches the
shared-freeze path after the previous weak snapshot has expired. Snapshot
construction is single-flight: one caller copies the shards while the others
reuse its result. Invalidation generations are shard-local, so insert misses on
different shards do not write the same counter cache line.

## Instruction-count comparison for derived field dispatch

For P3, Callgrind measured the same rustc command (nightly-2026-05-30,
optimized x86-64-v3 consumer) compiling a generated **64-field,
two-alias** `DeserializeIn` fixture. With `visit_str` delegating to the
existing byte matcher instead of emitting a second string-match table,
rustc executed **6,195,067,899 → 5,868,139,024** instructions
(**5.28% fewer**). This is the instruction cost of compiling that consumer,
not an estimated wall-clock build-time gain. The 64-field, one-struct,
two-alias source fixture was generated with local tooling that is not in
this repository, so the exact compile comparison cannot be rerun from this
checkout.

Matched Callgrind cases in `benches/internity_dispatch.rs` measured the
full one-field deserialization path (including lexicon construction), not
only the generated matcher. The `Ir` counts were:

| Field identifier | Before | Shared byte matcher |
|---|---:|---:|
| String: first / last / alias / unknown | 1,643 / 1,680 / 1,639 / 4,407 | 1,653 / 1,662 / 1,656 / 4,513 |
| Bytes: first / last / alias / unknown | 1,648 / 1,659 / 1,652 / 4,510 | 1,653 / 1,662 / 1,656 / 4,513 |
| Numeric | 1,639 | 1,640 |

The largest known-byte regression is 5 instructions (0.31%); unknown string
identifiers add 106 instructions (2.41%) on this error path. The compiler
instruction saving is the reason for retaining the change; it is not a
universal runtime-instruction win. Unknown-field policy, invalid UTF-8, and
aliases retain their Serde behavior.

## Provisional local measurements (not regression baselines)

One **unmatched**, single run of
`cargo +stable bench --package internity --bench internity_measure --all-features -- --full`
on 2026-09-23 (Linux x86_64 WSL2, AMD EPYC 7763, 16 logical CPUs,
rustc 1.97.1, working tree based on `e4733f81` with uncommitted internity
changes) produced:

| Operation | Observation |
|---|---:|
| 6,000-entry local / threaded retained heap | 176,144 / 286,784 bytes |
| 6,000-record local distinct serde decode→freeze→two exports | 3.20 ms; 78 allocations |
| 600,000-entry shared freeze | 19.33 ms; 9,968,968 newly allocated bytes |
| 6,000-entry 16-thread same-shard 99% hit workload (Fx hasher) | 1.47 million operations/s; p95 miss 989 µs |

Subsequent targeted `--quick` and `--freeze-smoke` runs on this host
exercised the added fixtures. A 6,000-record 64-field alias corpus took
**64.55 ms** through local JSON decode/freeze/export and **39.31 ms**
with the byte-identifier Serde fixture; the exported fields were checked
against the same canonical corpus in both cases. Shared freeze over 6,000
short versus long strings took **167 / 653 µs** and allocated
**102,690 / 630,690 bytes newly during the freeze**, excluding the retained
source table created before measurement. Those are single observations,
not an inferred runtime advantage for byte identifiers. The freeze matrix
also includes a 50/50 short/long mix at each corpus size; that mix has no
reported local baseline yet.

An uncommitted local measurement script compared the independent 64-field,
one-struct, two-alias consumer against its no-derive control after dependencies
were built on the same runner:

| Consumer | Clean consumer build | Incremental consumer build | Expanded Rust tokens | Binary bytes |
|---|---:|---:|---:|---:|
| No derives | 0.86 s | 0.86 s | 666 | 437,688 |
| `SerializeIn` + `DeserializeIn` | 3.92 s | 1.39 s | 33,759 | 620,016 |

The control-subtracted expansion adds **33,093 tokens**. A single
8-field/100-struct sample added 481,300 tokens; a 256-field/one-struct
sample added 128,709. Token counts use the pinned nightly's
`-Zunpretty=expanded` output parsed as `proc_macro2` tokens, not an
instrumented count inside the proc-macro. These are not matched
base/candidate data; the full 8/64/256-field × 1/100-struct × 0/2-alias
matrix and CI variance have not yet been measured. The fixture generator
and build measurement script are not included in this repository. The
concurrent benchmark reports throughput and miss tails, but leaves lock-wait
*share* ungated: operation latency alone cannot separate lock acquisition
from hashing and scheduler delay.

An earlier P3 prototype was reverted when its provisional wall-clock
measurements could not establish a reliable result. The matched
instruction-count comparisons above, rather than those provisional
observations, support the current dispatch change.

The shared-freeze measurement varied from 10.25 to 27.95 ms across local
runs, and the Fx same-shard p95 miss varied from 6.7 to 989 µs;
**no threshold is justified from these measurements**. The
local same-runner comparison tool is not included in this repository;
the current benchmark data do not establish a CI regression gate.
No production input distribution or matched base/candidate CI run has been
established for these provisional numbers.

For T8 (test infrastructure, **not** product performance), the selected
`freeze_races_writer_and_stays_prefix_consistent` test took **0.03 s**
under ordinary libtest on this host. The local duration-measurement script
is not included in the repository, and no per-case ordinary or Miri timing
gate is configured in CI. The existing prefix assertions remain; a CI
Miri per-case duration has not been collected for this report.

The established comparison timing figures below are wall-clock medians measured by Criterion. They are
machine-dependent: the ratios between rows are the durable signal, not the
absolute values.

This report is a curated set of customer-facing scenarios. The crate also carries
internal Callgrind instruction-count benches in the consolidated metabench target
(`benches/internity.rs`); the matched cases used above are part of that target.

**Workload:** a corpus of ≈6000 identifier-like strings, exercised through three customer operations — `insert` (interning a string for the first time), `reuse` (interning a string that is already interned) and `lookup` (resolving a handle back to its string).

**Methodology:** every timed region measures only insert/dedupe or lookup — benchmark setup and result destruction are kept outside the elapsed-time boundary. Refcounted `string_cache` atoms are retained across dedupe/lookup rounds so hits are measured against populated dynamic entries. `lookup` uses the same random order for all crates. The concurrent flavors run the operation on `n` threads and are barrier-timed, so thread spawn/join is excluded and only the parallel work is counted.  
**Δ vs internity:** `+x%` = that row is x% slower than internity on the same workload; `-x%` = faster.  
The process-global, cache-backed rows (`ustr`, `string_cache`) keep their table alive for the whole process, so they have no repeatable first-time `insert` timing and are absent from the single-threaded `insert` table.

## Memory footprint

Live heap bytes held by each interner, re-measured on 2026-09-24 with a
tracking global allocator over the same 6,000-string corpus
(`cargo bench --package internity --bench internity_mem`). `insert` is the
filled interner; `lookup` is the read structure the lookup benchmark resolves
against (the frozen read form where a crate has one). Lower is better.

```text
Corpus: 6000 distinct strings,     73.1 KiB of UTF-8 (avg 12.5 B/string)

== Owned interners — live heap held ==
  Interner                             insert       lookup
  internity  LocalLexicon           172.0 KiB     96.5 KiB
  internity  ThreadedLexicon        280.2 KiB     98.8 KiB
  lasso (live Rodeo)                264.2 KiB    264.2 KiB
  lasso (RodeoResolver)             264.2 KiB    224.2 KiB
  string-interner                   204.0 KiB    204.0 KiB
  symbol_table                      241.3 KiB    241.3 KiB

== Global caches — live heap held (persistent; insert == lookup) ==
  ustr                             8232.0 KiB
  string_cache                      351.7 KiB

Note: internity `lookup` is the frozen read form, which drops the string→handle map.
      lasso is reported as two rows: `live Rodeo` (matches the single-threaded `lookup`
      benchmark) and `RodeoResolver` (matches the `lookup-concurrent` `lasso-resolver`
      benchmark). `string-interner`/`symbol_table` have no frozen form so `lookup` == `insert`.
```

The filled `ThreadedLexicon` now retains more heap than the live `lasso`
entry (280.2 versus 264.2 KiB); its frozen lookup form retains 98.8 KiB.
