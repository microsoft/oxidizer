# Routerama benchmarks

Three families live in this directory. They answer different questions for
different audiences, and conflating them is how a benchmark suite stops being
believable. The file name tells you which family a target belongs to.

| Family | Name shape | Harness | Audience |
| --- | --- | --- | --- |
| Differential scenario | `routerama_<area>.rs` | Criterion | Customers |
| Instruction count | `routerama_<area>_cg.rs` | Gungraun / Callgrind | Us |
| Generated-size control | `routerama_<area>_size_<variant>.rs` | none (`fn main`) | Us |

## Differential scenario benchmarks

Criterion targets answer "how does Routerama compare to the alternative I would
otherwise pick, on a workload I recognize". They are scenario-oriented and
comparative, and they are the only family that reaches
[`docs/PERF.md`](../docs/PERF.md).

A Criterion target only earns a place in `docs/PERF.md` once it is differential
against at least one named competitor. Routerama-against-Routerama controls are
still worth keeping — they isolate the cost of one design choice — but their
results belong in [`docs/PERF-INTERNAL.md`](../docs/PERF-INTERNAL.md) alongside
the `_cg` counts, because a table with only our own name in it supports no
comparative claim.

## Instruction-count benchmarks

Callgrind targets find and prevent regressions in our own code, so they cover
every major functional area exhaustively and report a deterministic number
rather than a distribution. They never appear in a customer-facing document;
their results are published to
[`docs/PERF-INTERNAL.md`](../docs/PERF-INTERNAL.md).

Every `_cg.rs` target pairs with the Criterion target of the same base name and
carries the same scenario names — see
[`docs/callgrind-benchmarks.md`](../../../docs/callgrind-benchmarks.md) and
[`docs/naming.md`](../../../docs/naming.md).

## Generated-size controls

Targets carrying a `_size_` infix are not timing benchmarks at all. Each is a
standalone binary that exercises one representation choice and is measured by
its compiled size, so the cost of a code-generation strategy is attributable.
They must be built, not run; running one measures nothing.

Because the comparison is between binaries, every control in a set has to keep
its routed workload identical and vary only the representation under test —
which is why several of them share a fixture macro from `common/`.

The sets are:

- `routerama_literal_controls_size_{16,128,1024}` — generated code size against
  route count.
- `routerama_response_body_size_variants_{1,4,16,128}` — size against the number
  of distinct handler body types, with the route count pinned at 16 up to the
  16-variant point so the variant axis is isolated. These are generated; edit
  `tests/support/response_body_variants_codegen.rs` and run
  `scripts/generate_response_body_variants.rs`, never the fixtures themselves.

  128 is the top of this ladder deliberately. A 1,024-source fixture was built
  and did not finish type-checking in 18 minutes of CPU, so the generated
  per-source body sum is superlinear in the source count well before 1,024 and a
  checked-in target at that size would dominate every `--all-targets` build.
- `routerama_response_heads_size_*` and `routerama_response_heads_route_size_*` —
  the reserved, static-plan, generated, and ordinary response-head
  representations.
- `routerama_response_templates_size_*` — the exact, existing, and segmented
  template representations.
- `routerama_tower_size_*` — the exact, generated, and send-boxed Tower response
  boundaries.

## Shared fixtures

`common/` and `generated/` hold fixture code included by the targets above via
`include!`. They are not benchmark targets themselves.

## Where results are published

`scripts/perf_report.rs` writes both reports and owns only the regions between
`<!-- BEGIN GENERATED: name -->` and `<!-- END GENERATED: name -->` markers.
Everything outside a marker pair is hand-written and survives regeneration, so
prose, caveats, and dated provenance notes can be added anywhere in either file.

| Report | Contents | Regenerated by |
| --- | --- | --- |
| [`docs/PERF.md`](../docs/PERF.md) | Comparative wall-clock results only | every run |
| [`docs/PERF-INTERNAL.md`](../docs/PERF-INTERNAL.md) | Instruction counts, Routerama-only scenarios, size controls, acceptance gates | only when the Callgrind suite runs |

Running with `--no-gungraun`, or on a host without valgrind, leaves
`docs/PERF-INTERNAL.md` untouched instead of blanking columns.
